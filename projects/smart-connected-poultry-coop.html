overview

CoopMaster is a smart connected poultry-coop automation and monitoring system developed as an engineering graduation project. The objective was to design a low-cost, practical, and reliable solution capable of monitoring important environmental conditions inside a poultry coop while automating several repetitive tasks that normally require manual intervention. The project combines embedded systems, industrial-style automation, sensors, actuators, networking, cloud services, mobile application development, and local safety mechanisms into one integrated system. Rather than treating the poultry coop as a simple IoT demonstration, CoopMaster was designed around an engineering principle: the system should remain useful and safe even when the network or cloud service is unavailable. The system uses a Raspberry Pi 5 as the main local controller, Python for hardware and automation logic, sensors for monitoring, relays and actuators for physical control, Firebase for cloud synchronization, and a Flutter application for remote monitoring.

The Problem

Traditional small poultry coops often require the owner to manually perform several repetitive tasks. Depending on the installation, the owner may need to:

  • Check whether the coop door is open or closed
  • Open or close the entrance manually
  • Monitor environmental conditions
  • Check whether rain is occurring before opening an external entrance
  • Activate or deactivate watering equipment
  • Monitor the general operating state of the installation
  • React to abnormal conditions
  • Visit the coop physically to verify that equipment is operating correctly

The main challenge was designing a system in which: Sensors provide information → the controller interprets that information → automation logic makes decisions → actuators execute the required actions → the system reports its state to the user. This creates a complete closed-loop automation architecture.

Main Objectives

  • Environmental and state monitoring — collect information from sensors and determine the current state
  • Automatic door management — open and close the entrance automatically according to predefined conditions
  • Rain-aware operation — detect rain conditions and use this information to avoid inappropriate door operation
  • Motion detection — use a PIR sensor to detect movement in the monitored area
  • Watering control — control a water pump to activate watering-related equipment without direct manual operation
  • Remote monitoring — monitor through a graphical mobile interface
  • Local operation — retain essential functionality when Internet connectivity is unavailable
  • Safety — avoid blindly commanding actuators without verifying the state of the installation
  • Low-cost implementation — use accessible and relatively inexpensive components while applying engineering principles

System Architecture

CoopMaster is organized into several interconnected layers.

1. Physical Layer

Contains the real-world sensors and actuators. Sensors transform physical events into electrical signals that can be interpreted by the controller.

2. Control Layer

The Raspberry Pi 5 acts as the main local controller. It reads sensor inputs, processes sensor states, executes automation rules, controls actuators, monitors equipment states, handles local safety logic, communicates with the cloud layer, and provides information to the user interface.

3. Software Layer

The local control software was developed using Python. The raw GPIO states are converted into meaningful logical information.

4. Actuator Layer

The controller communicates with physical actuators through appropriate switching interfaces. Relay interfaces separate low-power control signals from higher-power actuator circuits.

GPIO Configuration

An important aspect of the prototype was defining a clear mapping between the Raspberry Pi GPIO pins and the physical devices.

GPIO Device Function
GPIO 5 PIR sensor Motion detection
GPIO 8 Rain sensor Rain detection
GPIO 7 Door relay Door opening command
GPIO 11 Door relay Door closing command
GPIO 25 Door state sensor Position/state feedback
GPIO 9 Door state sensor Position/state feedback
GPIO 10 Water control Watering control signal
GPIO 24 Pump Pump activation

The exact electrical implementation is separated from the software logic through the GPIO abstraction, making it easier to change hardware later.

Door Automation

One of the main functions of CoopMaster is automated door control. The door system is not treated as a simple OPEN = motor ON logic.

  1. User/automation requests OPEN
  2. Controller verifies current state
  3. Opening relay activated
  4. Motor moves door
  5. Position sensor provides feedback
  6. Controller detects target state
  7. Motor command stopped

This feedback-based architecture is important because an automation controller should ideally know whether the commanded action actually occurred.

Door Safety Logic

Safety was one of the most important design considerations. A naive implementation could simply activate a motor for a fixed amount of time, but this creates several problems.

  • Requested state
  • Commanded state
  • Feedback state
  • Actual operating condition

Instead of relying only on time, the system uses sensor information to determine whether the door has reached its intended state. This represents an important transition from simple remote control toward feedback-based automation.

Rain Detection

The rain sensor provides information about the external environmental condition. The controller can use this information as part of the automation decision. Conceptually: Rain sensor → Raspberry Pi → Automation logic → Door decision.

Motion Detection

A PIR sensor is used to detect movement. The sensor is connected to GPIO 5. The PIR signal allows the controller to determine whether motion has been detected in the monitored area.

Water Pump Control

CoopMaster also includes control of a watering system. The water-related control path uses: Controller → switching interface → pump. The pump can therefore be activated by software rather than requiring direct manual switching.

Local-First Architecture

One of the strongest engineering concepts in CoopMaster is its local-first architecture. Many IoT projects depend heavily on cloud services. If the Internet connection disappears, critical automation may stop functioning.

Cloud-dependent path: Sensor → Internet → Cloud → Application → Internet → Controller → Actuator

CoopMaster local path: Sensor → Raspberry Pi → Local automation → Actuator

Critical local functions

  • Sensor reading
  • Automation logic
  • Door control
  • Pump control
  • Safety logic

Connected functions

  • Remote monitoring
  • Data synchronization
  • User interface
  • Remote interaction
  • Cloud-based information storage

Firebase Integration

Firebase is used as the cloud connectivity layer. The Raspberry Pi communicates relevant system information to the cloud, while the Flutter application can use that information to provide the user with a remote view of the installation.

Flutter Mobile Application

A dedicated application was developed using Flutter. The application provides a graphical interface for interacting with the CoopMaster system. Instead of requiring the user to understand GPIO states, relay states, or Python processes, the application translates the technical information into a more understandable interface.

  • System status — a quick overview of the current installation state
  • Door control — the user can request opening or closing
  • Sensor information
  • Equipment status
  • Remote monitoring

Hardware-to-Software Communication

One of the most important aspects of CoopMaster is the complete communication chain between the physical world and the software. For example, consider the rain sensor:

  1. Physical event — Rain begins
  2. Sensor — The rain sensor changes its electrical state
  3. Raspberry Pi — The GPIO input detects the change
  4. Python — The Python control program interprets the signal
  5. Automation logic — The system determines what action should be taken
  6. Actuator — The relevant relay/motor state is controlled
  7. Firebase — The updated state can be synchronized
  8. Flutter — The user can see the updated condition in the application

Engineering Control Philosophy

Although CoopMaster is a small-scale project, its architecture follows principles found in industrial automation. The fundamental chain is: SENSOR → CONTROLLER → ACTUATOR.

The project demonstrates an understanding that automation is not simply about writing code or switching a motor. It requires understanding the relationship between physical processes, sensors, electrical signals, controllers, actuators, feedback, communication, safety, and user interfaces.

Instrumentation Perspective

From an instrumentation perspective, CoopMaster can be viewed as a small process-control installation. The physical environment represents the process. Sensors provide measurements or states. The Raspberry Pi acts as the control unit. Relays and motors provide the actuation layer. The Flutter application acts as the supervisory/user interface. Firebase provides the communication and remote data layer.

PROCESS → SENSORS → SIGNAL ACQUISITION → CONTROLLER → CONTROL LOGIC → ACTUATORS → PROCESS, with an additional monitoring path: CONTROLLER → CLOUD → USER APPLICATION.

Safety Philosophy

Safety was considered at both the software and system levels. The system should not assume that a command was successfully executed simply because a command was sent.

  • Requested state
  • Commanded state
  • Feedback state
  • Actual operating condition

Command: CLOSE DOOR does not automatically mean Door = CLOSED. The system should use feedback to determine the actual state. This distinction between commanded state and actual state is an important engineering concept.

Fault and Connectivity Considerations

A major consideration in the architecture was the possibility of communication failure. Internet connectivity can be interrupted for many reasons. Therefore, critical local functions should not depend on constant cloud availability.

Cloud failure: Remote monitoring may be temporarily unavailable, but the local automation can continue.

Local failure: This is more serious because the controller is responsible for physical automation.

Why Raspberry Pi?

The Raspberry Pi 5 was selected as the main controller because it provides a useful balance between processing capability, GPIO access, Linux environment, Python compatibility, networking, development flexibility, low cost, and availability.

A Raspberry Pi is not automatically equivalent to an industrial PLC. A PLC is designed specifically for industrial environments, deterministic control, electrical robustness, maintenance, and industrial communication.

Development Process

The project was approached as an integrated engineering system rather than as isolated software and hardware tasks.

  1. Step 1 — Identify the problem
    The first stage involved identifying repetitive manual operations that could benefit from automation.
  2. Step 2 — Define the system architecture
    The hardware and software components were organized into separate layers.
  3. Step 3 — Hardware integration
    The sensors and actuators were connected to the Raspberry Pi GPIO system.
  4. Step 4 — Develop the local controller
    Python was used to implement the local automation logic.
  5. Step 5 — Implement automation logic
    The automation rules were implemented so that sensor information could influence actuator behavior.
  6. Step 6 — Add cloud communication
    Firebase was integrated to synchronize system information and enable remote access.
  7. Step 7 — Develop the Flutter application
    A user interface was created to make the system understandable to a non-technical user.
  8. Step 8 — Testing and refinement
    The system was tested by observing the interaction between all components.

Challenges

The project involved several engineering challenges.

  • Hardware/software integration Working with physical hardware introduces problems that do not exist in purely software projects.
  • Actuator control Motors and pumps cannot be connected directly to Raspberry Pi GPIO pins.
  • Feedback Controlling a motor is relatively simple. Knowing when to stop it safely is more complicated.
  • Connectivity Cloud-based systems introduce network dependency.
  • Multiple technologies CoopMaster combines several technologies: Python + Raspberry Pi + GPIO + Firebase + Flutter.

Future Improvements

Although the prototype successfully demonstrates the core concept, several improvements could make the system more robust.

  • Industrial controller migration The Raspberry Pi could eventually be replaced or complemented by an industrial PLC.
  • ESP32-C3 version A future version could use an ESP32-C3 for selected sensor/actuator tasks.
  • Improved industrial communication Future versions could investigate Modbus RTU, Modbus TCP, MQTT, RS-485, and Industrial Ethernet.
  • More sensors Additional sensors could monitor temperature, humidity, water level, feed level, light level, electrical consumption, and motor current.
  • Historical data Firebase or another database could store long-term measurements.
  • Alarm management A future version could introduce an alarm system for abnormal conditions.
  • Predictive maintenance With enough historical data, the system could identify abnormal equipment behavior.

Final Project Summary

CoopMaster is a connected smart poultry-coop automation system designed to demonstrate how embedded electronics, instrumentation, automation, cloud technologies, and software development can be combined to solve a practical real-world problem. The most important architectural decision is the use of a local-first control philosophy.
